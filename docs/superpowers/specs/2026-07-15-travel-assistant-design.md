# GuideStick 出行场景对话与解释助手设计

## 目标

在不更换 ESP32-CAM 和 LU-ASR PRO 的前提下，把现有 DeepSeek 接入从简单的红绿灯标签映射，升级为面向视障出行的场景对话与解释助手。

用户通过 Android 客户端说话或输入文字。助手结合最近一次导盲杖识别到的环境状态回答问题，并由 Android 系统 TTS 朗读。红绿灯等安全结论继续由确定性规则控制，DeepSeek 不直接向设备下发通行指令。

## 非目标

- 本阶段不让 LU-ASR PRO 识别任意自然语言。它继续负责离线唤醒、固定命令词和固定语音。
- 本阶段不增加 I2S 麦克风、音频编解码器或新的主控板。
- DeepSeek 不直接控制紧急呼叫、LED 或通行状态。
- DeepSeek 不直接分析原始摄像头图像；它读取 YOLO 输出的结构化环境信息。
- 本阶段只支持单套比赛原型，不设计多导盲杖配网和设备绑定。

## 系统架构

```text
ESP32-CAM
  -> 上传图片
Django /android/identify/
  -> YOLO识别 red/green/no
  -> 保存最近环境状态和时间
  -> 按固定规则返回设备播报编号

Android AssistantActivity
  -> 系统语音识别或文字输入
Django /android/assistant/chat/
  -> 读取最近环境状态
  -> 执行安全规则
  -> 调用 DeepSeek 生成简短场景解释
  -> 返回回答和场景新鲜度
Android TextToSpeech
  -> 朗读回答
```

## 组件职责

### 最近环境状态

`/android/identify/` 在 YOLO 推理成功后，将以下数据写入 Django 缓存：

- `light`: `red`、`green` 或 `no`
- `command`: 设备使用的确定性指令
- `message`: 当前固定安全提示
- `captured_at`: 服务器收到图片的时间
- `source`: 识别来源

缓存键使用单例 `guidestick:latest_scene`。这符合当前只有一套比赛设备且没有设备 ID 的现状。后续增加设备绑定时再改为按设备 ID 存储。

### 对话接口

新增 `POST /android/assistant/chat/`：

请求示例：

```json
{
  "question": "我现在能过马路吗？",
  "history": [
    {"role": "user", "content": "前面是什么灯？"},
    {"role": "assistant", "content": "最近识别到绿灯。"}
  ]
}
```

约束：

- `question` 必填，去除首尾空白后不超过 200 个字符。
- `history` 可选，只接收最近 6 条用户和助手消息。
- 服务端忽略客户端提供的系统消息，系统提示完全由后端生成。
- 不把 API Key、内部异常或完整模型响应返回客户端。

响应示例：

```json
{
  "answer": "当前检测到绿灯，但系统尚未确认两侧车辆，请确认周围安全后通行。",
  "intent": "SAFETY_QUERY",
  "scene": {
    "light": "green",
    "age_seconds": 5,
    "fresh": true
  },
  "source": "deepseek"
}
```

### DeepSeek 对话客户端

新增独立对话函数，复用现有 DeepSeek 配置和 HTTP 连接方式，但使用面向出行助手的系统提示。输入包括：

- 用户当前问题
- 最多 6 条最近对话
- 最近环境状态及其时间差
- 系统能力边界：当前只能确认交通灯，不能确认车辆、路面和完整通行条件

模型回答限制为简短中文，不提供医疗、法律等无关长回答，不声称看到了结构化数据中不存在的目标。

## Android 交互

新增 `AssistantActivity`，从首页进入。页面包含：

- 对话记录列表
- 一个文本输入框
- 一个发送按钮
- 一个显著的麦克风按钮
- 正在聆听、请求中、朗读中和失败状态

语音输入使用 Android `RecognizerIntent`，需要 `RECORD_AUDIO` 权限。回答使用 Android `TextToSpeech` 朗读，不依赖 LU-ASR PRO 动态合成。

无障碍要求：

- 麦克风和发送按钮提供明确的 `contentDescription`
- 主要操作区域尺寸不小于 48dp
- 新回答到达后自动朗读，但提供停止朗读操作
- 语音识别失败时保留文字输入方式
- 网络请求期间禁止重复提交同一问题

## 安全规则

聊天接口不能成为设备控制接口。后端在调用模型前后执行以下规则：

1. 最近环境超过 30 秒视为过期。
2. 没有最近环境或环境已过期时，不回答“可以通行”，而是提示重新识别。
3. 最近结果为红灯时，任何通行安全问题都固定回答“检测到红灯，请停止通行”。
4. 最近结果为绿灯时，只能说明交通灯状态，必须明确尚未确认车辆、路面和其他风险。
5. 最近结果为 `no` 时，提示未识别到交通灯，不给出通行许可。
6. 对话接口不执行紧急呼叫。用户表达求助意图时，引导其使用现有紧急呼叫功能。
7. DeepSeek 请求失败、超时或响应无效时，返回基于最近场景的固定说明，HTTP 响应保持可用。

通行安全问题先通过本地关键词规则识别，包括“能不能走”“可以走吗”“能过马路吗”“安全吗”等常见表达。模型返回后再次检查禁止性表述，防止出现无条件通行建议。

## 现有识别接口调整

`/android/identify/` 保留现有响应字段，继续兼容 ESP32-CAM 和 Android。设备安全指令改为完全由本地规则生成：

- `red` -> `STOP`
- `green` -> `PROCEED`，语义限定为只确认交通灯状态
- `no` -> `CAUTION`

DeepSeek 不再位于每次图片识别的关键路径，从而降低延迟、API 消耗和网络失败对设备基础功能的影响。

## 错误处理

- 无问题文本：HTTP 400，返回可读错误。
- 语音识别失败：Android 显示失败状态并允许重试或输入文字。
- 无最近场景：聊天仍可进行，但明确提示当前没有可用环境信息。
- DeepSeek 超时或异常：使用固定场景说明并标记 `source: fallback`。
- TTS 初始化失败：仍显示文字回答，不影响聊天接口。
- Android Activity 退出时释放 `TextToSpeech` 和语音识别资源。

## 测试

### Django

- 保存和读取最近环境状态。
- 30 秒新鲜度边界。
- 红灯通行问题强制停止。
- 绿灯回答包含能力边界。
- `no` 和无场景不能给出通行许可。
- 对话历史长度和角色过滤。
- DeepSeek 成功、超时、无效响应和缺少配置的回退。
- 聊天接口不会触发紧急呼叫或设备控制。

### Android

- 请求与响应模型解析。
- 文本消息发送和错误状态。
- 麦克风权限允许与拒绝流程。
- 语音识别结果进入输入框并发送。
- TTS 初始化、朗读和 Activity 销毁释放。

### 手工演示

1. ESP32-CAM 上传红灯图片，随后询问“我能走吗”，回答必须停止。
2. 上传绿灯图片，随后询问相同问题，回答必须包含环境能力边界。
3. 等待超过 30 秒再询问，回答必须要求重新识别。
4. 关闭 DeepSeek 网络后询问，仍获得固定安全说明。
5. 在 Android 上完成说话、显示回答、自动朗读的完整流程。

## 验收标准

- Android 支持文字和语音两种方式连续提问。
- 回答能够引用 30 秒内最近一次交通灯识别结果。
- Android 能自动朗读回答并允许停止朗读。
- 红灯、过期、未识别和无场景情况下均不会给出通行许可。
- DeepSeek 不可用时基础识别、固定语音和聊天回退仍然工作。
- ESP32-CAM 和 LU-ASR PRO 现有功能保持兼容。
